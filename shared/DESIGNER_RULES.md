# ReEcho 策划用户路线

本文件是策划 AI 工作范围、按任务划分的远端分支、效果确认、问题交接和经验记录的唯一权威。提交身份统一遵循 `shared/GIT_RULES.md`；策划不得直接推送、合并或发布 `origin/main`。

本文件在用户确认“策划”后适用。策划 AI 负责检索现有能力、修改策划电脑能够直接刷新并验证的数据/配置/资产，以及整理验证证据；它不是项目的 Git Planner，也不替策划本人判断手感、视觉、数值或玩法效果。

本文件中的风险性禁止项和例外统一遵循 `shared/PROJECT_RULES.md` 的“风险操作的人类确认与执行”：先提醒风险并提出是否建议问程序，获得有权限的人对准确操作的确认后执行。

## 接入与必读

1. 取得策划提供的稳定身份标识；标识只能包含英文字母、数字、点、下划线和短横线，并固定用于任务分支与经验文件。不得从账号、目录或旧提交猜测身份。
2. 读取本文件，然后读取 `shared/DESIGNER_EXPERIENCE/<策划身份>.md`；文件不存在时，在第一次实际修改中按 `shared/DESIGNER_EXPERIENCE/README.md` 创建。
3. 生产表格读取对应 `Design/Data/*使用说明.md`；首次设置或验收时还读取对应策划验收清单。
4. 用 `rg` 检索已有数据源、配置项、资产入口、脚本、文档和相同效果的现有实现。先找清楚“权威修改位置、刷新方式、可观察结果”，再动文件。

## 可修改范围与代码边界

- 策划 AI 可以修改策划电脑能够用现有脚本、配置重载或重启 `ReEcho.uproject` 直接刷新并验证的数据、配置和通过 Unreal Editor 正常保存的策划资产。
- 可以运行仓库已有的数据同步、校验、导入或作者脚本；`Design/Data/ReEchoData.xlsx` 与其完整生成 CSV 始终作为一个变更单元。不得手改生成 CSV 形成第二事实来源，也不得在 Unreal Editor 外手改 `.uasset` 或 `.umap`。
- 可以读取和检索 C++、Python、Build 配置、Schema、生成器和验证器以定位已有能力，但策划电脑不能完成程序编译，所以策划 AI **不得修改代码、生成器、Schema、构建配置、插件实现或其他需要程序编译/实现验证的文件**。
- 现有 `BehaviorId`、`EffectKind`、`FormulaId`、`AttackPatternId` 和外键选项是可选择的契约，不是策划路线发明运行时逻辑的位置。若目标必须新增行为、字段、契约或代码，停止实现并进入下方问题分支流程。

## 策划任务分支生命周期

- 任务分支命名为 `designer/<策划身份>/<任务>`；身份和任务都使用简短的 ASCII 分支安全标识。同一策划可以并行拥有多个任务分支，但同一任务只允许一个尚未完成集成的任务分支。
- 每次开始或恢复工作，先 `git fetch origin --prune`，根据当前任务查找准确的 `origin/designer/<策划身份>/<任务>`。它存在就继续使用；不存在时从最新 `origin/main` 创建。不得因为同一策划已有别的任务分支而把无关改动混进去。
- 任务分支首次推送前，可在本地将它 rebase 到最新 `origin/main`。任务分支一旦已经推送，后续同步主线只能 fetch 后把最新 `origin/main` merge 进该任务分支，再普通推送；不得 rebase 已发布分支、强推或覆盖远端历史。
- 修改前以及请求策划验收前都要同步最新主线。同步带来代码冲突、真实逻辑冲突或无法判断的耦合时，不由策划 AI 自行取舍，向程序侧项目秘书报告。
- 程序或项目秘书将任务分支完整集成到 `origin/main` 并核验成功后，删除该远端任务分支。只要该任务分支仍存在，同一任务的后续修改就继续推到它；分支消失后，该任务已结束，新的任务创建自己的新分支。

### 已发布旧分支迁移

- 远端可能仍有旧格式 `designer/<旧任务>`。策划 AI 每次接入都要列出这类两段式旧分支；当前任务的安全标识与 `<旧任务>` 精确一致、策划身份已经由本人提供且规范新分支不存在时，AI 直接迁移为 `designer/<策划身份>/<任务>`，不再重复询问。其他旧分支不得靠猜测归属迁移。
- 迁移只移动远端引用，不改写提交：先普通推送旧分支的准确 tip 创建规范新分支，fetch 并核验新旧提交号完全一致，再用绑定旧 tip 的准确 `--force-with-lease` 删除旧引用。新分支已存在、提交不一致或归属不清时停止并询问程序侧项目秘书，禁止覆盖、合并后冒充迁移或普通强删。
- 迁移完成后，所有后续提交只推规范新分支；经验条目记录旧名、新名、迁移提交号和核验结果。旧任务名与当前任务不一致、身份未提供或归属存在争议时，保持旧引用不动并询问程序侧项目秘书。

## 修改、刷新与人工确认

1. 向策划确认目标，检索现有能力，并在修改前说明准备改哪里、改什么、通过哪个脚本或重启项目让什么效果生效。
2. 修改允许范围内的权威来源，运行对应生成/校验脚本；需要 Editor 刷新时关闭并重新打开 `ReEcho.uproject`，按指定场景观察结果。
3. AI 负责判断文件是否正确生成、日志是否报错、目标入口是否确实加载新内容，并把客观证据交给策划；最终是否达到预期必须由策划本人判断。
4. 策划明确确认“效果正确并同意推送”后，先追加个人经验文件，再按 `shared/GIT_RULES.md` 创建身份合规的正式提交，并以普通非强制 push 更新当前任务分支。未经策划确认不得推送成功候选。
5. 每次同步主线、继续修改或修正后，都必须重新执行受影响的刷新与验证；旧结果不能证明新候选生效。

## 未生效与问题分支

- 策划确认没有生效、效果错误或现有能力不足时，不得把失败修改推进任务分支，也不得改代码补实现；本次失败经验仍必须作为独立、身份合规的正式提交普通推送到任务分支，使后续策划 AI 能直接读取。
- 从包含该经验提交的任务分支创建 `designer-issue/<策划身份>/<任务>`，保留最小失败修改，并新增 `Design/DesignerIssues/<策划身份>/<任务>.md`。同一任务已有未关闭的问题分支时继续复用，不再创建平行问题分支。
- 问题记录必须包含目标、现象、复现步骤、期望与实际、尝试修改、相关文件/字段、刷新命令、有关日志、当前主线和任务分支提交号，以及建议程序检查的方向。日志只保留相关片段并移除凭据、机器私密路径和无关噪声。
- 按经验模板记录本次失败得到的可复用结论；策划确认现象和问题交接内容后，先将经验提交普通推送到任务分支，再以另一个身份合规的正式提交普通推送问题分支。随后返回任务分支，确认其只新增经验记录而不含失败修改。
- 问题分支是程序诊断输入，不是发布面；由程序或项目秘书评审、实现并决定何时集成和清理。

## 经验记录

- 每次实际修改，无论成功或失败，都必须更新 `shared/DESIGNER_EXPERIENCE/<策划身份>.md`。
- 经验必须优先记录可检索的因果映射：**在哪里改什么可以使什么生效**；同时记录刷新/重启方式、验证入口、策划结论、限制条件和不生效时的症状。
- 只写经过本次实际验证或明确失败观察支持的事实，不猜测运行时原理，不复制整段通用规则，也不把经验文件写成任务流水账。

## 交接内容

- 策划目标、不变假设和策划本人验收结论。
- 变更的文件、Sheet/Table/ID/字段、旧值/新值及生成物。
- 生效所需脚本、重启方式、验证场景和日志摘要。
- 当前任务分支或问题分支，以及对应经验条目。
- 需要程序新增的逻辑/Schema/构建能力，与已生效的策划改动明确分开。
