# ReEcho 策划用户路线

本文件是策划 AI 工作范围、Bug/需求登记、远端协作分支、效果确认和经验记录的唯一权威。提交身份统一遵循 `shared/GIT_RULES.md`；策划不得直接推送、合并或发布 `origin/main`。

本文件在用户确认“策划”后适用。策划 AI 负责与策划澄清问题、检索现有能力、修改策划电脑能够直接刷新并验证的数据/配置/资产，以及整理可复现证据；它不是项目的 Git Planner，也不替策划本人判断手感、视觉、数值、玩法效果或需求取舍。

本文件中的风险性禁止项和例外统一遵循 `shared/PROJECT_RULES.md` 的“风险操作的人类确认与执行”：先提醒风险并提出是否建议问程序，获得有权限的人对准确操作的确认后执行。

## 接入与必读

1. 取得策划提供的稳定身份标识；标识只能包含英文字母、数字、点、下划线和短横线，并固定用于协作分支、Issue 目录和经验文件。不得从账号、目录或旧提交猜测身份。
2. 读取本文件，然后读取 `shared/DESIGNER_EXPERIENCE/<策划身份>.md`；文件不存在时，在第一次实际修改中按 `shared/DESIGNER_EXPERIENCE/README.md` 创建。
3. 生产表格读取对应 `Design/Data/*使用说明.md`；首次设置或验收时还读取对应策划验收清单。
4. 用 `rg` 检索已有数据源、配置项、资产入口、脚本、文档和相同效果的现有实现。先找清楚“权威修改位置、刷新方式、可观察结果”，再动文件。

## 可修改范围与代码边界

- 策划 AI 可以修改策划电脑能够用现有脚本、配置重载或重启 `ReEcho.uproject` 直接刷新并验证的数据、配置和通过 Unreal Editor 正常保存的策划资产。
- 可以运行仓库已有的数据同步、校验、导入或作者脚本；`Design/Data/ReEchoData.xlsx` 与其完整生成 CSV 始终作为一个变更单元。不得手改生成 CSV 形成第二事实来源，也不得在 Unreal Editor 外手改 `.uasset` 或 `.umap`。
- 可以读取和检索 C++、Python、Build 配置、Schema、生成器和验证器以定位已有能力，但策划电脑不能完成程序编译，所以策划 AI **不得修改代码、生成器、Schema、构建配置、插件实现或其他需要程序编译/实现验证的文件**。
- 现有 `BehaviorId`、`EffectKind`、`FormulaId`、`AttackPatternId` 和外键选项是可选择的契约，不是策划路线发明运行时逻辑的位置。若目标必须新增行为、字段、契约或代码，完成对应 Issue/Request 登记后交给程序，不由策划 AI 补实现。

## Issue 与 Request 登记

Bug 和需求都是类似 Plan 的正式输入记录，但不分配 Plan 编号。每个策划在 `issues/` 下使用自己的目录；报告文件名只由名称和简要描述组成，不添加编号、日期或状态前缀：

- Bug：`issues/<策划身份>/bugs/<名称>-<简要描述>.md`，远端登记分支为 `issue/<策划身份>/<简述>`。
- 需求：`issues/<策划身份>/requests/<名称>-<简要描述>.md`，远端登记分支为 `request/<策划身份>/<简述>`。
- `<简述>` 使用简短的 ASCII 分支安全标识；MD 文件名可以使用准确中文。报告正文使用 `issues/TEMPLATE.md` 的字段，不另建自定义格式。

### Bug 提交流程

1. 策划先与本地 AI 交流，明确 Bug 实际出现在哪个本地或远端分支及准确提交号；不得只写“最新版”“我的分支”或凭印象归因。
2. AI 在该准确提交上协助复现，记录运行环境/构建类型、前置条件、复现步骤、出现频率、期望、实际现象和影响范围；不能复现时如实写明尝试过程，不伪造结论。
3. 收集对应会话日志。优先保存覆盖该会话的完整日志到 `issues/<策划身份>/bugs/logs/<报告简述>/`；提交前移除凭据、用户私密路径和无关隐私。日志过大或含大量无关噪声时，只保留完整覆盖复现时间段的片段，并在 MD 中注明原始日志文件名、截取时间范围、关键标记和未提交部分。
4. 从 Bug 出现的准确源提交创建或复用唯一的 `issue/<策划身份>/<简述>`，加入 MD 和对应日志。Issue 分支保留复现基线，不混入猜测性修复；源提交不在 `origin/main` 时，报告必须明确源分支、源提交和相对 main 的差异来源。
5. 策划本人确认现象描述、复现步骤和日志对应无误并明确同意推送后，AI 才能按 `shared/GIT_RULES.md` 创建身份合规的正式提交并普通推送 Issue 分支。未经确认不得把 Bug 登记发布为团队输入。

### 需求提交流程

1. 策划先与本地 AI 交流，把口头目标整理为当前行为、目标行为、适用场景、明确排除项、验收标准、依赖和可能影响面，并记录需求提出时所在的源分支及准确提交号。
2. 从该准确源提交创建或复用唯一的 `request/<策划身份>/<简述>`，写入 `issues/<策划身份>/requests/<名称>-<简要描述>.md`。有运行现象或参考日志时保存到 `issues/<策划身份>/requests/logs/<报告简述>/`；需求没有运行日志时允许不附日志，但必须在 MD 中写“无运行日志”及原因。
3. 策划本人确认需求描述和验收标准准确并明确同意推送后，AI 才能按 `shared/GIT_RULES.md` 创建身份合规的正式提交并普通推送 Request 分支。AI 不把自己的实现建议写成已经确认的产品决定。

## Merge 分支生命周期

- 所有准备交给程序集成的策划实际修改统一使用 `merge/<策划身份>/<简述>`。`issue/...` 只登记 Bug，`request/...` 只登记需求，二者都不是待合并实现候选。
- Bug 或需求发布后，如果现有能力足以在策划允许范围内完成修改，则从对应 Issue/Request 的准确 tip 创建 `merge/<策划身份>/<简述>`；如果报告源本来就是同一事项的 Merge 分支，则把报告提交带回并继续复用该 Merge 分支，不创建平行候选。
- 每次开始或恢复工作，先 `git fetch origin --prune`，按策划身份和简述查找准确远端分支。分支存在就继续使用；不存在才从对应登记分支创建。一个事项每种类型只允许一个未关闭分支，不得将无关事项混入同一分支。
- 分支首次推送前，可在本地 rebase 到最新 `origin/main`。任何协作分支一旦已经推送，后续同步主线只能 fetch 后把最新 `origin/main` merge 进该分支，再普通推送；不得 rebase 已发布分支、强推或覆盖远端历史。
- 修改前、恢复工作时、请求策划验收前以及最终推送前都要同步并审计最新主线。同步带来物理冲突、真实逻辑冲突或无法判断的耦合时，不由策划 AI 自行取舍，向程序侧项目秘书报告。
- AI 负责判断文件是否正确生成、日志是否报错、目标入口是否确实加载新内容，并把客观证据交给策划；最终是否达到预期必须由策划本人判断。
- 策划明确确认“效果正确并同意推送”后，先追加个人经验文件、更新报告状态和证据，再按 `shared/GIT_RULES.md` 创建身份合规的正式提交并普通推送 Merge 分支。未经策划确认不得推送成功候选。
- 每次同步主线、继续修改或修正后，都必须重新执行受影响的刷新与验证；旧结果不能证明新候选生效。

## 未生效与程序交接

- 策划确认没有生效、效果错误或现有能力不足时，不得把失败修改推进 Merge 分支，也不得改代码补实现；更新对应 Bug/需求报告，准确记录尝试修改、相关文件/字段、刷新命令、现象、日志和建议程序检查方向。
- 本次失败得到的可复用经验仍写入 `shared/DESIGNER_EXPERIENCE/<策划身份>.md`。策划确认交接内容后，将报告、日志和经验按 `shared/GIT_RULES.md` 创建身份合规的正式提交，普通推送到原 `issue/...` 或 `request/...` 分支；失败修改只保留在本地或经明确需要作为最小复现材料时留在登记分支，不得冒充待合并候选。
- Issue/Request 是程序诊断和排期输入，不授权策划 AI 修改代码，也不自动代表产品接受、优先级或实现方案。涉及程序实现或权限疑问时向程序侧项目秘书交接。

## 关闭、留档与清理

- 报告状态至少记录“待确认、已确认、处理中、待合并、已解决、已拒绝”之一；“已拒绝”必须来自有权作产品取舍的人，AI 不自行判定。
- 进入 main 的最终 Merge 候选必须包含对应报告、已提交日志索引、策划验收结论、Merge 分支和提交号。集成者在报告中补充最终 main 提交号与结果；MD 和已提交日志作为历史永久保留，不因关闭而删除。
- 程序或项目秘书确认 Merge 分支已完整进入 `origin/main`、报告和日志也已留档后，删除对应 `merge/...`、`issue/...` 和 `request/...` 远端分支。未合入、归属不明、仍有独有提交或可能被他人继续使用的分支不得删除。

### 已发布旧分支迁移

- 旧 `designer/<策划身份>/<任务>` 迁为 `merge/<策划身份>/<任务>`；旧 `designer-issue/<策划身份>/<任务>` 迁为 `issue/<策划身份>/<任务>`。两段式 `designer/<旧任务>` 仅在策划身份已由本人提供、任务标识精确匹配且规范新分支不存在时迁为 `merge/<策划身份>/<任务>`；不得靠猜测归属迁移。
- 迁移只移动远端引用，不改写提交：先普通推送旧分支的准确 tip 创建规范新分支，fetch 并核验新旧提交号完全一致，再用绑定旧 tip 的准确 lease 删除旧引用。新分支已存在、提交不一致、旧分支在迁移期间变化或归属不清时停止并询问程序侧项目秘书，禁止覆盖、合并后冒充迁移或普通强删。
- 迁移完成后，所有后续提交只推规范新分支；经验条目记录旧名、新名、迁移提交号和核验结果。旧引用保持不动的事项必须明确报告，不得静默遗留两套活跃名称。

## 经验记录

- 每次实际修改，无论成功或失败，都必须更新 `shared/DESIGNER_EXPERIENCE/<策划身份>.md`。
- 经验必须优先记录可检索的因果映射：**在哪里改什么可以使什么生效**；同时记录刷新/重启方式、验证入口、策划结论、限制条件和不生效时的症状。
- 只写经过本次实际验证或明确失败观察支持的事实，不猜测运行时原理，不复制整段通用规则，也不把经验文件写成任务流水账。

## 交接内容

- 对应 Bug/需求报告、源分支与准确源提交、登记分支、Merge 分支及提交号。
- 策划目标、不变假设、验收标准和策划本人结论。
- 变更的文件、Sheet/Table/ID/字段、旧值/新值及生成物。
- 生效所需脚本、重启方式、验证场景、日志文件和关键时间范围。
- 对应经验条目，以及需要程序新增的逻辑/Schema/构建能力。
