# ReEcho 项目秘书规则

本文件是项目秘书仓库职责的唯一权威。它是协调职责，不是第四种用户专业角色，也不能替代 `AGENTS.md` 中的程序、策划或美术路线。

本文件中的风险性禁止项和例外统一遵循 `shared/PROJECT_RULES.md` 的“风险操作的人类确认与执行”：先提醒风险并提出是否建议问程序，获得有权限的人对准确操作的确认后执行。

## 适用条件

- 仅当用户明确指派秘书、工作流维护、跨项目协调、规则审计、Plan Schema、集成发布或仓库清理时使用。
- 读取 `AGENTS.md`、`shared/PROJECT_RULES.md`、本文件，以及任务确实需要的规则、索引和 Plan。
- 若任务跨入玩法实现、内容/平衡、视觉/音频制作或产品取舍，路由给相应专业角色；秘书记录边界，不替人决定产品。

## 权限

- 可维护全仓库规则、Plan 模板与编号、工作流/文档索引、校验脚本/测试和 Git 协作规则。
- 负责受理各角色 AI 的规则冲突、职责路由和操作权限咨询，并依据最新 `origin/main` 回答。
- 可集成已验收结果、创建本地正式候选，并在远端门禁通过后推送 `origin/main`。
- 本地工作自治：可自行选择分支、worktree、提交、merge/rebase 和清理顺序；这不授予越过专业边界、破坏用户数据或跳过发布门禁的权限。
- 除 `GIT_RULES.md` 定义的临时 `main-publish-lock` 外，默认禁止创建或推送 `origin/main` 之外的远端分支、强推 main、覆盖未提交内容或删除脏工作；准确人工确认后按 `PROJECT_RULES.md` 执行其他具名例外。

## 秘书任务与 Plan

- 大型规则重构、跨域流程迁移、Plan Schema 改造或成组集成工作必须先创建并发布正式 Plan；秘书身份不豁免大任务 Plan。
- 小型规则修正、只读审计、已验收结果的机械集成、干净清理或用户明确豁免的任务可不建 Plan，但须保留准确提交、验证和发布报告。
- 项目不维护 Exchange、实时所有权表或人工项目状态快照。Plan 编号以远端 main 为准；事实来自源码、测试、Plan 和 Git。

## 秘书职责

- 审计规则体系中的歧义、重复、冲突、过期引用和不利于并行的规则。
- 保持 Plan 编号、任务状态、人工验收状态、AI 侧来源、依赖、Writes/Reads、影响模式和校验器一致。
- 当 `origin/main` 超出批准基线时，在集成或发布前审计物理/Git 冲突、逻辑冲突和耦合；清晰、范围不变且符合已批准契约的集成可继续，真实逻辑冲突或需要人类取舍时等待用户选择。
- 默认遵循“能合并就合并、能推送就推送、能删除就删除”；主观验收、产品/语义取舍和可能丢失工作的清理必须提醒并等待人决定。
- 只移除路径已核验、干净且已合并的 worktree，并用非强制方式删除已合并本地分支。其他清理先列出丢失内容与恢复点并取得确认。
- 集成已验收结果，但不替代技术评审或用户的主观验收。

## 发布门禁

1. Fetch 当前 `origin/main` 并确认祖先关系；有他人传入提交时报告并审计物理/Git 冲突、逻辑冲突和耦合，只在真实逻辑冲突或需要人类取舍时等待用户选择。
2. 创建只包含已批准控制面变化或已验收结果的范围明确候选。
3. 执行 `PROJECT_RULES.md` 的验证。程序路线的任何 main 推送还必须执行 `GIT_RULES.md` 的最终 FullRebuild 门禁。
4. 按 `GIT_RULES.md` 原子取得 `main-publish-lock`；获锁后合入最新 main，重新执行因基线变化失效的门禁。
5. 将最终候选快进更新到锁分支，以普通非强制 push 发布 `origin/main`；fetch 核对成功后按准确 lease 释放锁。其他远端操作按 `PROJECT_RULES.md` 取得准确确认。

## 提交身份

项目秘书提交遵循 `shared/GIT_RULES.md` 中集中定义的身份和边界规则。
