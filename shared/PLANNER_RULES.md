# ReEcho Planner 规则

本文件定义规划、评审、集成与发布职责。它适用于独立 Planner，也适用于一个 AI 同时规划和执行的情况。启动顺序由 `AGENTS.md` 定义，硬规则位于 `PROJECT_RULES.md`。

本文件中的风险性禁止项和例外统一遵循 `shared/PROJECT_RULES.md` 的“风险操作的人类确认与执行”：先提醒风险并提出是否建议问程序，获得有权限的人对准确操作的确认后执行。

## Plan 语言

- 从本规则生效后，新建 Plan 及对现有 Plan 的实质性内容更新必须使用中文正文。
- 代码、命令、路径、类型/函数/字段名、稳定 ID、分支名、提交号和固定状态枚举保持原文。
- 不得仅为翻译而批量重写已关闭历史 Plan；再次实质更新时同步中文化所修改的语义章节。

## 执行前编号并发布 Plan

所有大任务都必须先发布正式 Plan，无论是否采用 Planner-Executor 模式，也无论规划者和执行者是不是同一个 AI。

1. 分配 Plan 编号前，fetch `origin/main`，从该远端引用列出 `plans/<id>-*.md`，识别最大 Plan 编号。远端 main 是编号权威；编号不复用，新任务使用远端最大值之后的下一个空闲编号。
2. 若远端 main 包含批准基线之外的他人提交，先执行下方外部提交集成审计；用户决定前不得 pull、merge、rebase、cherry-pick 或 push。
3. 写作前搜索代码、数据和对应 `CODEBASE_MAP` 路线；引用具体路径，不依赖记忆。
4. 将锁定目标/验收与实现建议分开。实现者可以优化细节，但不得暗中修改目标、验收或公共契约。
5. 从 `plans/TEMPLATE.md` 记录负责人、AI 侧来源、生命周期、人工验收、基线、依赖、Writes/Reads、影响模式、兼容承诺和排除项。Writes/Reads/影响模式是影响面说明，不是远端写锁。
6. 程序 Plan 在发布前必须完成“架构影响与设计决策”：列出受影响 `MOD-*` / `AREA-*`、对应模块文档、设计意图、权威状态/契约/依赖影响和 `CODEBASE_MAP` 同步范围。每个被修改或受公共契约影响的 Runtime Module 文档都必须加入 `Writes`；新增模块计划创建 `modules/MOD-<Name>.md`。缺失时不得设为 `Ready`。
7. 一旦分配正式编号，立即将编号 Plan 单独发布到 `origin/main`；不得夹带实现或无关 WIP。发布 Plan 不需要任何 Exchange、广播分支或所有权行。
8. Fetch 并核验 `origin/main` 包含准确 Plan 后才开始实质实现。若推送被拒或其他已发布 Plan 占用编号，再次 fetch，将尚未发布的冲突 Plan 及其后续本地 Plan 整体移到远端新最大值后的首个连续区间，更新文件名、标题、依赖和仍有效的实时引用后重试。
9. 小型、边界清晰的修复、只读审计或用户明确豁免的任务可以不建 Plan；不得把跨模块、公共契约或成组功能伪装成轻量任务。

## 本地执行

- Plan 发布后，本地工作方式自由：直接工作、分支、worktree、stash、WIP 提交、merge 和 rebase 均可由当前成员/AI按本地需要选择。隔离 worktree 是并行建议，不是权限门禁。
- 同一克隆需要 Editor/命令独占时使用 `EXECUTOR_RULES.md` 的 Git-common-dir Unreal 锁。
- 扩张目标、验收或公共契约时先更新 Plan；普通实现偏差和证据写入执行记录。
- 跨机器不维护实时所有权。其他成员从已发布 Plan 了解意图；实际差异在 pull/push 边界审计并由用户取舍。

## 外部提交集成审计

当 fetch 发现 `origin/main` 包含当前已批准本地基线之外的他人提交时，在 pull、merge、rebase、cherry-pick 或 push 前停止；即使 Git 可以快进或干净合并也不例外。

1. 识别传入提交、作者、关联 Plan、基线和变更路径。
2. 评估**物理/Git 冲突**：用只读 log、diff、merge-tree 和祖先检查定位同行编辑、add/add、重命名、modify/delete、二进制/生成文件碰撞；没有文本冲突时也明确说明。
3. 评估**逻辑冲突**：比较目标、人工决定和运行时语义，识别旧逻辑被继续扩展、公共 API/Schema/稳定 ID/存档/生成器契约分叉、事实来源变化、矛盾测试或一方暗中恢复/覆盖另一方行为。
4. 评估**耦合**：列出受影响 Plan、Writes/Reads、共享契约、下游本地工作、集成顺序和失效的构建/测试/人工证据。
5. 评估 Plan 编号冲突。远端编号优先；尚未发布的本地 Plan 有序后移，不重写已发布历史。
6. 报告传入范围、物理/Git 冲突、逻辑冲突、耦合、编号变化和选项：`remote`、`local`、`combined adaptation`、`defer/split`，给出权衡与建议。
7. 等待用户选择后只集成所选结果，检查意外删除/恢复并重跑受影响验证。
8. 推送前立即再次 fetch；若 main 又前进，重新审计并报告新增耦合。

## Executor 提示模板

Plan 是任务规格；启动提示只是中立路由外壳。不得赋予新身份、覆盖接收 AI 现有本地角色。不得重复 Plan 的锁定目标、验收、Writes、排除项和验证矩阵。只有对方无法访问 Plan 时才嵌入范围。

```text
这是 ReEcho `plans/<id>-<name>.md` 的启动引导，不改变你现有的身份或职责。
先按 AGENTS.md 完成或复用本对话已确认的专业角色路由，再读取该 Plan 的最小上下文。
以 `<approved-base>` 为批准基线；本地分支/worktree/提交组织由你按仓库规则自行决定。
按 Plan 实现、验证、维护相关模块文档并更新执行记录。若必须改变锁定范围或公共契约，停止越界部分并报告。
完成后报告候选提交/工作树、验证、风险和剩余人工验收；不要自行推送远端引用。
```

## 评审、集成与清理

默认将满足门禁的工作推进到最远状态：能合并就合并、能推送就推送、能删除就删除。“能”表示范围、验证、人工决定、外部变化、发布和清理门禁全部满足。

1. 审查 Plan 状态、批准基线、实际 diff、锁定验收、客观证据、公共契约和代码健康；返工时回到 `InProgress`。
2. 小型、明确、范围内的评审修正可直接完成；大型、不确定、独立可并行或需要新一轮设计的变化应更新原 Plan 或创建新 Plan。
3. `PendingBeforeClose` 必须由用户解决；`PendingFollowUp` 只在用户明确延期时保留。
4. 关闭前审阅相关 `CODEBASE_MAP`：拓扑/依赖/跨模块不变量变化时更新 `ARCHITECTURE.md`，路由变化时更新 `README.md`，并维护所有直接修改和受契约影响的 `modules/MOD-*.md`。每份相关文档必须在 Plan 记录“已更新：具体变化”或“已审阅、无需修改：原因”；未记录完整审阅结果不得设为 `Closed`。
5. 本地合并策略由当前成员决定；合并后复查最终候选，不能让整分支带入已过时或无关内容。
6. 只有路径准确、状态干净且必需变化已集成/另处保留时，才非强制移除 worktree 并用 `git branch -d` 删除已合并分支。脏 worktree、未合并分支或强制删除须报告会丢失的内容和恢复点，等待人工确认。

## 远端 main 发布

`origin/main` 是唯一允许的远端分支。编号 Plan 在大任务执行前发布；实现是否使用本地分支由成员自行决定。

- 鼓励小批量、较频繁地推送 main，缩短队友等待和差异窗口。
- Plan-only 发布和已完成的权威规则/工作流发布在静态验证及外部审计通过后可直接进行；不得夹带实现或无关 WIP。
- 程序路线每次推送 `origin/main` 都必须在准确最终候选上通过 `shared/GIT_RULES.md` 的 `-FullRebuild` 与精选预构建包门禁，包括仅文档/规则的程序推送。
- 正式提交进入远端前必须按 `GIT_RULES.md` 使用当前人类账号 + AI 身份和且仅一个专业标签。本地 WIP 历史可在发布前 squash/reword/重新提交为合规候选。
- 推送前立即再次 fetch。无新他人提交时，验证通过即可非强制推送；有新他人提交时重新执行外部审计并等待用户选择。
- 发布后 fetch 并核对本地/远端 main。默认不创建、推送或保留其他远端引用；强推、创建/删除远端引用按 `PROJECT_RULES.md` 做风险确认。

## 共享记忆关闭

评审/关闭时仅在相关情况下更新：

- `CODEBASE_MAP/ARCHITECTURE.md`：每次必审；拓扑或跨模块不变量变化时更新。
- `CODEBASE_MAP/README.md` 与 `CODEBASE_MAP/modules/MOD-*.md`：同步模块设计意图和代码落点。
- `LESSONS.md`：只加入带来源 Plan、可复用且有证据的经验。
- 指定 Plan：最终生命周期、行为变化、证据、风险和人工验收结果。

项目不维护 Exchange 或人工项目状态快照；当前事实来自源码、测试、已发布/关闭 Plan 和 Git。
